# PlanMaster

A VS Code extension that displays a queue of work kept in plain-text lane files. Currently in the design phase: specification, prompts, examples and a mockup. See [README.md](README.md).

## Language

Everything in this repository is in English: code, comments, identifiers, documentation, UI strings, prompts, examples and commit messages. No other language anywhere.

## Git rules

- Commit locally when asked. **Never push**, and never add a remote, unless the user explicitly asks.
- **Never refer to Claude, Anthropic, an AI assistant or any "generated by" statement in commit metadata.** This covers commit subjects and bodies, trailers (no `Co-Authored-By`, no `Generated with`), tag messages, branch names, and pull request titles and descriptions. It applies to every commit, whatever default attribution a tool suggests. The user's instruction overrides such defaults.
  - The rule is about commit metadata only. The documentation of the Claude Code integration naturally names Claude and is fine.
- Commit messages: imperative mood, subject at most 72 characters, no trailing period, a body only when the reason is not obvious. One logical change per commit.
- Do not commit scratch files, build output or dependencies (see `.gitignore`).

## Development method

Work in small Red-Green-Refactor cycles.

1. **Red.** Write one failing test for the next behavior. Run it and see it fail for the right reason.
2. **Green.** Write the least code that makes it pass.
3. **Refactor.** Clean up with the tests green, then run the smell analysis.

A bug is fixed by first writing the test that reproduces it. Pure refactoring needs no new test, but if the code to be changed is not covered, add characterization tests first.

### Tests follow FIRST

| Principle | How it is enforced here |
|---|---|
| **Fast** | The unit project runs in about a second; a unit test slower than 1 s fails (`testTimeout`). Anything that builds or spawns a process belongs to the integration project. |
| **Independent** | No test relies on another. `npm run test:shuffle` runs them in random order. Files are created in per-test temporary directories. |
| **Repeatable** | No dependence on the clock, the network or the machine. Time is passed in. `npm run test:tz` runs the suite in five time zones. |
| **Self-validating** | Every test asserts; none needs a human to read output. |
| **Timely** | Tests are written before the code (Red first), not after. |

### Commands

| Command | Purpose |
|---|---|
| `npm test` | Unit tests. |
| `npm run test:integration` | Builds `out/` and runs the command-line checker as a subprocess. |
| `npm run typecheck` | Compiler without emitting. |
| `npm run smells` | ESLint (typescript-eslint strict, SonarJS), jscpd (duplication), knip (dead code). |
| `npm run coverage` | Unit tests with coverage thresholds (95% lines, 90% branches). |
| `npm run bundle` | Bundles the extension into `dist/extension.cjs`. |
| `npm run test:extension` | Runs the extension inside a real VS Code, headless through xvfb. Set `VSCODE_EXECUTABLE` to choose the binary. |
| `npm run check` | Everything above plus shuffle, time zones, integration and the extension tests. Run before every commit. |

### Code smells

`npm run smells` must report nothing. Limits: cyclomatic complexity 10, cognitive complexity 12, 50 lines per function, 4 parameters, nesting depth 3, 300 lines per file. Do not silence a rule with a comment to get past it; restructure the code. If a limit is genuinely wrong, change it in `eslint.config.js` in a commit of its own, with the reason.

### Code conventions

- TypeScript with `strict` and `noUncheckedIndexedAccess`. ES modules, imports use the `.js` suffix.
- Layout: `src/core` is pure (no `node:` and no VS Code imports), `src/app` holds the editor-independent application logic behind ports (no VS Code imports), `src/node` reads files, `src/cli` is the command-line entry point, `src/webview` runs inside the queue view page (DOM only, no Node or editor API), `src/extension` is the only code that imports `vscode` and contains translation only. `test/` mirrors them; what needs a real editor is in `scripts/extension-tests`.
- Every lint rule has a test for the case that triggers it and for the nearest case that does not.
- The prompt documents in `docs/prompts` are bundled into the extension as text (see `src/extension/templates.ts`), so editing them changes what the commands copy. Keep each to exactly one ```text block.
- Commands are written as flows over ports (`src/app/commands`) and tested with a scripted user interface; `src/extension` only supplies the real dialogs, diff, clipboard and file access.
- Parsing must stay linear in the length of its input. Avoid regular expressions with overlapping quantifiers.
- Match the surrounding code: comments only where the reason is not obvious from the code.

## Source of truth

- `docs/spec/queue-format.md` is normative. The parser, linter, prompts, examples and mockup must agree with it. When they disagree, fix them, not the specification, unless the specification is what is wrong.
- A change of behavior is made in this order: specification, prompts, examples, mockup. Prefer one commit per coherent change.
- A change to the grammar, a marker's meaning or a required token bumps the `format` version (see queue-format, section 13).

## Consistency checks before committing

- Every queue line shown in any document parses under the grammar in queue-format section 4.2.
- The demo workspace yields exactly the findings listed in its README.
- The prompts in `docs/prompts/` and the strings in `docs/mockup/queue-view.html` (managed block and lane start prompt) are identical in content.
- The managed block stays under 350 words.

`npm test` checks all four, in `test/docs.test.ts` and `test/demo.test.ts`.

## Principles to keep

- The extension never writes to a lane file. Its views are read-only.
- The files are the only source of truth. No parallel store.
- Only `src/extension` imports the VS Code API. Logic goes in `core` or `app`, where it is unit tested.
- Text from lane files is untrusted. It is escaped everywhere it is displayed.
