# Queue format, version 1

Status: draft, normative. The parser, the linter, the prompts and the examples in this repository must all agree with this document. If they disagree, this document wins and the other file has a bug.

## 1. Purpose

Claude Code sessions do long pieces of work, and the person supervising them loses track of what is in progress, what is blocked and what is finished. The queue is a plain-text, human-editable, machine-parseable record of that work. It is written by the people and sessions doing the work and read by the PlanMaster extension, which only ever displays it.

Design goals:

- **One source of truth.** The files are the data. The extension keeps no copy that can drift.
- **Easy to write correctly.** One item per line, a small closed grammar, no nesting rules beyond indentation.
- **Safe to edit with a text tool.** A change of state touches one line. Nothing in the format forces a whole-file rewrite.
- **Readable without tooling.** A queue file is useful in any editor or in a `git diff`.

Non-goals for version 1: free-form notes inside the queue, per-item comments, priorities other than file order, due dates, assignees other than the `wait:` target, and any kind of write-back from the extension.

## 2. Concepts

| Term | Meaning |
|---|---|
| **Lane** | A long-lived Claude chat that owns one area of work. It has a short ID and a descriptive title. A lane owns exactly one queue file and is the only writer of that file. |
| **Item** | A unit of work that takes hours or days and spans sessions. Not a micro-step; micro-steps belong in the session's own todo list. |
| **Queue** | All items of all lanes in a workspace. |
| **Marker** | The character between brackets that gives an item's state. |
| **Token** | A `key:value` pair at the end of an item line. |

## 3. Workspace layout

```
<workspace>/
  .planmaster/
    config.json            optional, shared settings (section 11)
    FORMAT.md              short grammar reference for Claude, generated by the extension
    lanes/
      A.md                 one file per lane, file name = lane ID
      B.md
    archive/
      A.md                 closed items moved out of the live file (section 10)
```

Rules:

- The lanes directory is `.planmaster/lanes/` unless `config.json` overrides it.
- A lane file is named `<LANE_ID>.md`, and its `lane` front-matter value must equal the file name without extension.
- Files are UTF-8, LF line endings, no BOM.
- The `.planmaster/` directory is intended to be committed to version control. It is the history of the work.

## 4. Lane file structure

A lane file is a front-matter block followed by item lines.

```markdown
---
format: 1
lane: B
title: Automated checks, gates and ratchets
---

- [~] B-12 Survey existing checks (gate or ratchet, cost, frozen debt) ref:ROUND-4 since:2026-11-02T10:55
  - [x] B-12a List ratchets with frozen debt done:2026-11-02T11:02
  - [~] B-12b Measure the cost of each check since:2026-11-02T11:05
  - [ ] B-12c Write the table for the runner proposal
- [ ] B-13 Add a signing-key check to diff-prod-staging.mjs ref:R-198
- [!] B-14 Make the rules fingerprint a ratchet once permissions land wait:B-12 since:2026-11-01T17:30
- [x] B-09 Verify the backup bucket copy done:2026-10-30T12:50
```

### 4.1 Front matter

The first line is `---`. Then exactly the keys below, one per line as `key: value`, then a closing `---`. This is a line-based subset of YAML, not full YAML: the value is the rest of the line, trimmed, taken verbatim. Colons in the value are fine.

| Key | Required | Rule |
|---|---|---|
| `format` | yes | Integer. `1` for this document. |
| `lane` | yes | Lane ID: `[A-Z][A-Z0-9]{0,3}`. Must equal the file name. |
| `title` | yes | One line, 3 to 80 characters. A precise description of the lane's area, not a slogan. "Automated checks, gates and ratchets" is good. "Misc" and "Stuff for Bob" are not. |

Unknown front-matter keys are ignored by the parser and reported as a warning (PM017).

### 4.2 Item lines

After the front matter, blank lines and HTML comments (`<!-- ... -->`, single line) are ignored. Every other line must be an item line (PM016 otherwise).

Grammar, as a regular expression with named groups:

```
^(?<indent>(?: {2})*)- \[(?<marker>[ ~!x-])\] (?<id>[A-Z][A-Z0-9]{0,3}-[0-9]+[a-z0-9]*) (?<rest>\S.*)$
```

`rest` is split into title and tokens by reading words from the right: while the last whitespace-separated word matches `^(ref|wait|since|done):\S+$`, it is a token and is removed. What remains is the title. Consequences:

- Tokens must be at the end of the line, after the title.
- Token values contain no spaces.
- Titles may contain colons and any other characters, but must not end with a word that looks like a known token.
- The same key may appear only once per line (PM001).
- Canonical token order is `ref`, `wait`, `since`, `done`. The parser accepts any order; tools that write lines use the canonical order.

Indentation is two spaces per level. The first item of a file is at level 0, a child is exactly one level deeper than its parent, and the maximum level is 3 (so four levels in total: 0, 1, 2, 3). Anything else is PM001 or PM019.

## 5. Markers

| Marker | State | Meaning |
|---|---|---|
| `[ ]` | todo | Not started. |
| `[~]` | in progress | Someone is working on it now. |
| `[!]` | blocked | Cannot continue until something outside the lane happens. |
| `[x]` | done | Finished. |
| `[-]` | dropped | Abandoned on purpose. Kept for the record, counted as closed. |

`done` and `dropped` are the two **closed** states. Everything else is **open**.

## 6. Tokens

| Token | Meaning | Value |
|---|---|---|
| `ref:` | Link to something outside the queue: a plan, a ticket, a document, an ID in another system. | Free, no spaces. Several references are comma-separated: `ref:P-017,C-57`. |
| `wait:` | What a blocked item is waiting for. | A person key from `config.json` (`people`), or an item ID from any lane. |
| `since:` | When the item entered its current state. | Timestamp. |
| `done:` | When the item was closed (done or dropped). | Timestamp. |

### 6.1 Timestamps

`YYYY-MM-DDTHH:MM`, local time of the machine the work runs on, no seconds, no zone. Example: `2026-11-02T11:48`. Writers produce it with `date +%Y-%m-%dT%H:%M` and never from memory or inference.

### 6.2 Which tokens each state allows

| Marker | `ref` | `wait` | `since` | `done` |
|---|---|---|---|---|
| `[ ]` | optional | not allowed | not allowed | not allowed |
| `[~]` | optional | not allowed | required | not allowed |
| `[!]` | optional | required | required | not allowed |
| `[x]`, `[-]` | optional | not allowed | not allowed | required |

A token that is required and missing is an error (PM004, PM005, PM006). A token that is present where it is not allowed is a warning (PM013), because a leftover token after a state change is common and harmless.

`since:` on a blocked item records when it became blocked. When an item moves from `[~]` to `[!]` the writer replaces the `since:` value.

## 7. State changes

The linter only sees the current file, so it does not enforce transitions. These are the intended edits for writers:

| From | To | Edit |
|---|---|---|
| `[ ]` | `[~]` | Marker, add `since:`. |
| `[ ]` | `[!]` | Marker, add `wait:` and `since:`. |
| `[~]` | `[x]` | Marker, remove `since:`, add `done:`. |
| `[~]` | `[!]` | Marker, add `wait:`, replace `since:`. |
| `[~]` | `[ ]` | Marker, remove `since:`. (Parking an item.) |
| `[!]` | `[~]` | Marker, remove `wait:`, replace `since:`. |
| `[!]` | `[x]` | Marker, remove `wait:` and `since:`, add `done:`. |
| any open | `[-]` | Marker, remove `wait:` and `since:`, add `done:`. |
| `[x]`, `[-]` | `[~]` | Marker, remove `done:`, add `since:`. (Reopening.) |

Items are never deleted from a live file except by archiving (section 10). An item that was never started and is no longer wanted may be dropped with `[-]` like any other.

## 8. Hierarchy and order

- A child belongs to the nearest preceding line with a smaller indent.
- **At most one top-level `[~]` item per lane.** It is the lane's focus. Violation: PM008.
- **At most one `[~]` among the children of one parent**, and likewise among top-level items. Violation: PM009.
- A closed parent must have only closed children. Violation: PM010.
- An open `[ ]` parent with a `[~]` child is suspicious: the work started but the parent says it did not. Warning PM011.
- A `[~]` parent may have any mix of children.
- File order is priority order. The first top-level `[ ]` item is "up next". Writers do not reorder items unless asked to.
- Closed items stay where they are until archived. They are not moved to the bottom.

## 9. IDs

- Format: `<LANE_ID>-<number><suffix>`, for example `B-12`, `B-12a`, `B-12a1`.
- A top-level item takes the next number after the highest number used in the lane's live file **and** its archive file.
- A child takes its parent's ID plus a suffix: letters at the first child level (`B-12a`, `B-12b`), digits at the second (`B-12a1`), and so on alternating. The linter only requires the shape of the ID, not that it extends the parent's; extending it is the convention.
- IDs are unique across the whole workspace, including archive files (PM002), and a lane's IDs must carry the lane's prefix (PM003).
- IDs are never reused, even after an item is dropped or archived.
- An ID is the stable handle for every purpose: links between items (`wait:`), tool anchors, and search.

## 10. Archive

`archive/<LANE_ID>.md` has the same front matter and grammar as the live file. Archiving moves a **whole subtree** whose items are all closed, preserving the subtree's internal order, once its closing time is older than `archiveAfterDays`. Archived IDs remain reserved and resolvable: the linter reads archive files for PM002 and PM007, and the extension ignores them for views.

Archiving is performed by the session that owns the lane, on request (see the archive prompt), never by the extension.

## 11. Configuration

`.planmaster/config.json`, optional, committed. All keys optional.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `format` | integer | `1` | Format version the workspace uses. |
| `people` | string array | `[]` | Valid `wait:` person keys. Lowercase, no spaces. Keys are compared case-sensitively. |
| `staleAfterMinutes` | integer | `120` | Threshold for the stale warning (PM012). |
| `doneVisibleDays` | integer | `3` | How long closed items stay visible in the Stack view. |
| `archiveAfterDays` | integer | `14` | Age after which closed subtrees are eligible for archiving. |
| `lanesDir` | string | `.planmaster/lanes` | Directory of lane files, relative to the workspace root. |

A `config.json` that is not valid JSON, or whose keys have the wrong type, is a configuration error reported by the tools. Defaults are not silently substituted for a broken file. Unknown keys are ignored.

## 12. Lint rules

The linter is a pure function of the lane files, the archive files, `config.json`, the file modification times and the current time. Each finding has a code, a severity, a file, a line and a message.

| Code | Severity | Rule |
|---|---|---|
| PM001 | error | Malformed item line: bad marker, bad ID, odd indentation, a child more than one level deeper than its parent, an empty title, or a repeated token key. |
| PM002 | error | Duplicate ID in the workspace, archive included. |
| PM003 | error | ID prefix differs from the lane ID. |
| PM004 | error | `[!]` item without `wait:`. |
| PM005 | error | `[x]` or `[-]` item without `done:`. |
| PM006 | error | `[~]` or `[!]` item without `since:`. |
| PM007 | error | `wait:` target is neither a configured person nor an existing item ID. |
| PM008 | error | More than one top-level `[~]` item in a lane. |
| PM009 | error | More than one `[~]` item among the children of the same parent. (Top-level items are covered by PM008.) |
| PM010 | error | Closed parent with an open child. |
| PM011 | warning | Open `[ ]` parent with a `[~]` child. |
| PM012 | warning | Stale: a top-level `[~]` item whose `since:` is older than `staleAfterMinutes` **and** whose file has not been modified for longer than `staleAfterMinutes`. |
| PM013 | warning | Token present where the state does not allow it (section 6.2). |
| PM014 | error | Timestamp does not match `YYYY-MM-DDTHH:MM` or is not a real date. |
| PM015 | warning | Timestamp is more than five minutes in the future, or more than five minutes later than the file's modification time. A real edit cannot record a time after it happened, so this usually means the time was guessed. Not checked when the modification time is unknown. |
| PM016 | warning | Line is not blank, not a comment and not an item. |
| PM017 | error | Front matter missing, malformed, wrong `format`, missing keys, or `lane` different from the file name. Unknown keys are a warning. |
| PM018 | warning | `wait:` points to an item that is already closed; the block is probably resolved. |
| PM019 | error | Nesting deeper than level 3. |
| PM020 | warning | Title longer than 120 characters. Long context belongs in a document linked with `ref:`. |
| PM021 | error | A lane or archive file could not be read, or is larger than 1 MB and was not parsed. |

## 13. Versioning

- `format` is an integer in every lane file and in `config.json`.
- Adding an optional token or a lint rule that only warns does not change the version.
- Changing the grammar, a marker's meaning or a required token does.
- The extension supports the current format and the one before it, and offers a migration command when it meets the older one.
- Unknown `format` values newer than the extension's make the extension show the file as unreadable instead of guessing.

## 14. Worked example

The directory `docs/examples/demo-workspace/` contains five lanes in this format and a `config.json`. Two diagnostics in it are intentional:

- `B.md`, item `B-14`: blocked without `wait:` (PM004).
- `E.md`, item `E-05`: in progress since 08:05 with the file untouched since 08:07, which is stale (PM012) when the current time is 11:48 on the same day.
